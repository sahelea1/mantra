# Mantra — design notes

This is the plan behind the code: what Mantra is for, how it is built, and why each decision was made. It covers the engine, protocols, resilience and configuration model; the README covers usage. Updated for v0.3.1 (chain of command, escalation to the planner, revision-resume, periodic review, hand stops, liveness).

## 1. Goals and non-goals

**Goals.** One app that feels unified whether you run one agent or a team of them; every configured model available everywhere, through whichever runtime can reach it (Codex or Claude Code); model, effort and context tunable live; multi-agent workflows that are *configurable* (by hand or by an agent) rather than hard-coded; performance and robustness good enough to leave running for an hour against flaky APIs — and to survive Mantra itself being killed; works in ordinary Linux and macOS terminals.

**Non-goals.** Re-implementing an agent loop (Codex and Claude Code already have good ones); a web UI; Windows; hiding the git workflow from the user (runs land as an ordinary branch you can inspect).

## 2. Architecture

```
┌──────────────────────── mantra (one process, tokio, 2 worker threads) ──────────────────────────┐
│  input thread ──► AppEvent ◄── Hub events ◄── one task per agent ──► codex app-server (child)     │
│                     │                              │                  JSON-RPC over stdio         │
│                     │                              └───────────────► claude -p (child)            │
│                     ▼                                                stream-json over stdio,      │
│   App (state, routing, approvals, commands)                          tools via `mantra mcp-bridge`│
│     ├── Agent reducers: protocol notifications → renderable items, tokens, plan, file stats      │
│     ├── Run = the Conductor (deterministic state machine for Mandala)                             │
│     │     acts only through the `Ctx` trait: spawn / spawn_resumed / prompt / interrupt /        │
│     │     compact / stop / tool_result / set_effort / job (blocking git work off-thread) / notify │
│     │     persists `state.json` at every transition; `engine/resume` rebuilds a Run from it       │
│     └── UI: pure draw functions over App state (ratatui), redrawn only when dirty/animating       │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Source map: `rpc.rs` (JSON-RPC transport, stderr filter), `hub.rs` (process supervision, exit codes, crash restarts) + `hub/claude.rs` (the Claude Code process and its event translator), `bridge.rs` (`mantra mcp-bridge`: the stdio MCP server a Claude agent talks to), `agent.rs` (per-agent state + reducer), `engine/` (`pattern`, `plan`, `tools`, `git`, `run` = Conductor, `state` = persisted snapshot, `resume` = safe-boundary restart), `app.rs` (glue), `ui/` (screens), `mock.rs` (simulated Codex), `discover.rs`, `config.rs`, `util.rs`.

## 3. Key decisions

**Rust, single binary.** Needed for "performant, not laggy, not bloated": no runtime, ~4 MB, starts instantly. ratatui + crossterm cover every mainstream Linux/macOS terminal.

**Drive the vendors' own agent runtimes, one process per agent.** Codex's app-server protocol (verified against Codex 0.154.0) gives threads, turns, steering, interrupts, compaction, approvals, token usage, diffs and plan updates — everything a UI needs — while keeping Codex's own loop, sandbox, auth and provider support. One process per agent costs some memory (~30–60 MB each) but buys crash isolation: a wedged or crashed agent is restarted alone (exponential backoff, max 5 restarts per 10 min, then it parks until you press `r`) and **resumes its thread**, while the rest of the team keeps working. Crash lines carry the exit code and the last useful stderr line; Codex's known chatter (`OutputTextDelta without active item`, …) is filtered and repeated lines are collapsed.

**One seam for backends.** Claude Code is driven the same way — `claude -p --input-format stream-json --output-format stream-json --verbose --dangerously-skip-permissions --session-id <uuid> --model … --autocompact …` (verified against Claude Code 2.1.269) — and `hub/claude.rs` translates its NDJSON events into the *same* notification methods `Agent::apply` already understands (`item/started`, `item/agentMessage/delta`, `item/completed`, `thread/tokenUsage/updated`, compaction items, `turn/completed`). The reducer, the Conductor and the UI have no backend branches; the only backend-aware code is the spawn (`app::spawn_agent` resolves `ProviderKind`) and the two process modules. Steering mid-turn is a stdin message (Claude delivers it at the next tool boundary), interrupt is a `control_request`, `/compact` is the literal `/compact` line (recognised by its `compact_boundary` event), crash restart is `--resume <session>`. `--dangerously-skip-permissions` is always passed: a pipe can't answer Claude's permission prompts, and Mantra's isolation comes from git worktrees and read-only roles instead (as root, Claude additionally requires `IS_SANDBOX=1`). Auth is either the user's subscription login or `--bare` + `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL` for third-party gateways — which is also the escape hatch for gateways that reject Codex's `developer` role.

**Tools reach Claude through MCP.** Codex has dynamic tools in its protocol; Claude Code does not, so each Claude agent gets `--strict-mcp-config --mcp-config` pointing at `mantra mcp-bridge --sock … --agent <id>`: a tiny stdio MCP server (same binary) that forwards `tools/list` and `tools/call` over a Unix socket in `$MANTRA_HOME/run/` to the running Mantra, which turns them into the same `item/tool/call` requests the Conductor already answers. Tools appear as `mcp__mantra__<name>`; the reply travels back over the socket. Nothing about the tool semantics changes.

**Mechanics in code, judgment in models ("the Conductor").** Spawning, waiting, retrying API errors, saving outputs, merging, running checks, archiving threads and advancing phases are done by a deterministic Rust state machine, not by an LLM looping over "check status" calls. LLM agents are only woken when judgment is needed, and they act through **dynamic tools** that Mantra executes: `mantra_submit_plan`, `mantra_revise_plan`, `mantra_spawn`, `mantra_prompt`, `mantra_retry`, `mantra_interrupt`, `mantra_set_effort`, `mantra_pause_agents`, `mantra_resume_agents`, `mantra_status`, `mantra_log`, `mantra_read_phase`, `mantra_brief_orchestrator`, `mantra_spawn_adhoc`, `mantra_gate_report`, `mantra_wait` (plus `mantra_read_pattern`/`mantra_write_pattern` for the architect). Tool guards refuse what can't be right (prompting a worker whose task is done once the phase moved on; a fourth prompt to the same idle worker within five minutes respawns it instead). Safety nets back up the models, e.g. tasks the orchestrator forgot to spawn are started automatically.

**Every agent that should be working is working (the watchdog).** `Run::expected_active()` derives from the stage who must be busy and why. An idle expected agent climbs a ladder — nudge it (`watchdog_seconds`), respawn the orchestrator or wake it about the idle agent (`watchdog_escalate_seconds`), wake the planner (2×), then halt — with every rung journaled. Any run agent can be respawned in place (`Run::respawn`): the old process is stopped, a fresh one is spawned with a `[mantra:respawn]` prompt carrying the current state, and the phase/round it was in is preserved.

**Decisions travel up the chain of command.** `mantra_ask` is available to every worker, gate and finale agent (→ the orchestrator) and to the orchestrator (→ the planner); the planner has `mantra_ask_user` (→ a soft question band on the stage, answered by the user's next message — the run keeps going). `Run::pending_questions` marks the asker as waiting: its idle turn end without a `STATUS:` line is not "done", `expected_active()` skips it and expects the rung above instead (`Expect::Answering` for a planner that owes the orchestrator an answer), and the answer — `mantra_prompt` to the asker, `mantra_brief_orchestrator` for the orchestrator — clears it and bypasses the idle-prompt guards. Halts the run cannot fix itself (`GateExhausted`, `AttemptsExhausted`) go through `halt_and_escalate`: the planner gets the failing checks, their output and the last report, and exactly three moves — `mantra_revise_plan` (`apply_revision` re-opens tasks changed after they were done, sends a phase already merging/gating back to `Orchestrating`, and `resume_by(planner)` un-halts), `mantra_resume_run(note)` (one more attempt, note to the stuck agent), `mantra_ask_user`. `spawn_task`/`retry_worker` refuse while halted. `review_tick` hands the idle orchestrator a per-worker digest every `review_minutes`.

**A hand stop outranks every self-healing path.** `Agent::stopped_by_user` is set only by the two user interrupts (`ctrl+c`, `x` — never by `Run::halt`, `mantra_interrupt` or `mantra_pause_agents`, which have their own resume paths) and cleared at exactly one choke point, `app::prompt_agent`: talking to an agent *is* telling it to carry on. While set, `Run::on_turn_done` returns before the retry ladder, the planner nudge, the gate round, the worker report and the finale step; `on_ready` skips the post-restart resume prompt; `watchdog_tick` steps over it; `status_text` marks it. This is what keeps the engine from undoing a deliberate stop — the failure it fixes had three separate paths (nudge, transient retry, resume) putting a stopped planner back to work within seconds.

**Liveness is shown, not inferred.** The CLIs tick while a model reasons (Claude Code emits `thinking_tokens` every 1-2s), so `Agent::last_event` standing still is the one honest "is it stuck?" signal: `ui::quiet_for` surfaces it past 20s on the status line and the agent card, and `watchdog_tick` journals one line per silent spell for a busy non-worker agent past `stall_minutes` (workers keep `tick`'s tripwire, which also wakes the orchestrator). The tick's own running count goes into the activity label (`thinking · 9.4k`) so the number visibly climbs. Claude Code's `autocompact_state` announces the account's real context window seconds after spawn; a subscription login trusts it over the configured guess, an `api_key` gateway does not.

**Halts are typed.** There is no `paused` flag. Everything that stops a run goes through `Run::halt(reason, agent, message)` with `HaltReason::{User, Auth, UsageLimit, ProviderRejected, Environment, GateExhausted, AttemptsExhausted, AgentTurnFailed}`; the reason drives the band's hint (`m` to switch a rejected model, `r` to retry an environment fix, `space` to resume a user pause) and `resume()` is the single way back. `ProviderRejected` (HTTP 400/422, "unexpected message role") is never retried. Two consecutive identical gate blockers halt (`GateExhausted`) rather than burn the remaining rounds; the first `bwrap`/user-namespace failure halts (`Environment`) with the sysctl fix — and the same probe runs once at startup, before a run can start.

**The plan is a validated contract.** The planner submits JSON matching a schema: phases → tasks (`id`, `title`, `role`, `scope` globs, self-contained `prompt`, `acceptance`, optional `effort`) + a per-phase gate (`checks`, `focus`, `criteria`) + `final_checks` + `orchestrator_brief`. Mantra validates it (unique ids, known worker roles, non-trivial prompts, per-phase task caps, and **pairwise-disjoint scopes for parallel tasks**) and returns human-readable rejections so the planner fixes them itself. Revisions are diffed against the running phase so completed work is kept.

**Isolation by git worktrees.** Each run gets an integration worktree on branch `mantra/<run>`; each parallel worker gets its own worktree on `mantra-w/<run>/<task>-<attempt>` (a separate namespace, since git can't nest refs under an existing branch). At the gate Mantra commits and merges each worker branch (`--no-ff`); conflicts go to the QA gate agent, whose sandbox is widened to the integration worktree via `writable_roots`. Out-of-scope edits trip a wire that wakes the orchestrator. `isolation = auto` falls back to a shared directory for non-git projects; if a single worktree can't be created, that worker runs on the integration copy (safe because scopes are disjoint). `/land` merges the run branch into your branch only when your tree is clean; `mantra runs delete` removes worktrees, branches and the journal.

**Runs are resumable.** `state.json` is a typed `RunState` (stage, workspace, workers with worktree/branch/report, agents with thread ids, completed phases) rewritten atomically at every transition and whenever an agent's thread id becomes known. `engine/resume` rebuilds a `Run` from it and restarts at the nearest **safe boundary** rather than replaying what the old process was mid-way through: Planning → planner re-attached to its thread (`Ctx::spawn_resumed`) and asked to submit; Review → the saved plan back up for review; a working phase → a fresh orchestrator briefed with the phase status, running workers re-attached when their worktree still exists (`thread/resume` / `--resume`) or re-spawned with the same prompt; merging/checks/gate → the idempotent merge → checks → gate sequence again; handoff → next phase; finale → the step again; done/failed → read-only. Old v0.1 `state.json` files (untyped stage) are listed but refused.

**Context management.** Every agent is launched with an explicit window and compaction threshold — the model's numbers or an assumed 200k / 85% (marked as assumed in the UI): `model_context_window`/`model_auto_compact_token_limit` for Codex, `--autocompact` for Claude — so a 16k model compacts instead of dying, and a worker that still overflows on an assumed window gets it halved for the next attempt. Compaction is shown honestly: Codex reports it as a `contextCompaction` item (plus a deprecated `thread/compacted` twin, which Mantra ignores when the item is present); Claude as `compact_boundary` with pre/post token counts. Mantra records the size before, amends the item with the size after, and treats a turn that contains *only* a compaction as housekeeping, not as "the agent finished" — otherwise the Conductor would mistake a compaction for a completed planner/orchestrator/worker turn. A `/compact` sent mid-turn is deferred to the end of the turn. Workers are short-lived and archived after their phase (report and exit status saved first). The orchestrator is reset per phase with a compact handoff (or compacted in place: `orchestrator_context = fresh|compact`).

**Messages queue behind a turn.** In every chat (Solo, zoom, `@name`), `⏎` while the agent is mid-turn queues the message (visible chip) and delivers it when the turn ends; `ctrl+f` force-steers it into the running turn now. The engine's own prompting (`Send::Auto`) keeps steering immediately, as before; only user-originated sends carry `Send::Queue|Force`.

## 4. The default workflow as a state machine

```
Setup ─► Planning ─► Review ─► Phase[i]: Orchestrating ─► Merging ─► Checks ─► Gate(round ≤ N) ─► Handoff ─┐
            ▲  (user feedback)                                                                             │
            └──────────── re-prompt: planner may pause agents / revise plan / brief orchestrator ◄─────────┤
                                                                                   next phase ◄────────────┘
                                                               last phase ─► Finale[step…] ─► Done | Failed
   any stage ─► Halt{reason} ─► resume()          any stage ─► state.json ─► (new process) resume at a boundary
```

The finale is a list in the pattern (default: heavy QA → security → planner verification with `may_spawn = true`). The whole flow is data: roles, which role plans/orchestrates/gates/handles re-prompts, and the finale chain are all editable in the Studio.

## 5. Resilience and cost control

| failure | handling |
|---|---|
| stream drop / overload / 429 / 5xx | the CLI retries the stream; Mantra then retries the turn with backoff (4s, 8s, …), up to `worker_retries + 1` |
| context window exceeded | compact, then continue; halve an *assumed* window for the next attempt |
| 401 / 403 / usage limit | **halt** (`Auth`/`UsageLimit`), alert + desktop notification, `space` resumes |
| HTTP 400/422, "unexpected message role" | **halt** (`ProviderRejected`), never retried; `m` switches the role's model and resumes |
| `bwrap` / user-namespace failure | **halt** (`Environment`) on the first one, with the sysctl fix; probed at startup too |
| planner / orchestrator / gate turn fails otherwise | one free respawn, then **halt** (`AgentTurnFailed`) — never nag in a loop |
| gate keeps failing, repeats the same blocker, or the same check fails identically twice | **halt** (`GateExhausted`) and **escalate to the planner** (revise / resume with a note / ask the user) |
| worker fails for good | reported to the orchestrator, who may steer or respawn; **hard cap** of `worker_retries + 3` attempts per task across every path, then **halt** (`AttemptsExhausted`) and escalate; `r` or the planner grants one more |
| a worker or gate is unsure | `mantra_ask` up one rung; it waits, the rung above is expected to answer |
| an expected agent goes idle | watchdog ladder: nudge → respawn/wake orchestrator → wake planner → halt |
| codex / claude process crash | restart that agent only, resume thread/session; parks after 5 crashes / 10 min |
| worktree creation fails | fall back to the shared integration copy |
| stall / token budget / out-of-scope edit | tripwire event to the orchestrator |
| Mantra itself dies | `mantra runs resume <id>` from the last `state.json` |

Unrecognised errors are classified from the message (401/403/forbidden → auth; 400/422/invalid request → provider-rejected; 429/502/503/disconnect → transient). Every turn Mantra starts is tracked (`awaiting_start`), so prompts sent during a turn start are queued and delivered as steering; failed steers are re-queued for the next turn. Starting a run pre-flights every role's provider (missing key, unknown alias) so no turn is spent on a `Missing environment variable` error.

## 6. Performance

Rendering is event-driven: the loop redraws only when state changed or something is animating (capped at `fps`, default 12); an idle Solo session renders at 0 fps. Bursts of streaming deltas are drained (up to 512 events) before a single redraw. Rendered lines are cached per item (invalidated by version, width, verbosity), and the log renders bottom-up so only visible items are laid out. Item history is capped per agent (3000, oldest trimmed). Animations are pure functions of time. Blocking git work runs on `spawn_blocking`. `state.json` is a few KB written atomically (temp + rename) on transitions only.

**Terminal robustness.** Drawing happens inside `catch_unwind` (the panic hook skips terminal restoration while drawing), so a layout bug shows a one-line notice instead of killing every agent. Layout arithmetic is saturating throughout and verified by rendering all screens at 13 sizes in a debug build. Frames are wrapped in synchronized-output sequences. Under tmux, Mantra avoids the prefix key (`ctrl+t` toggles panels), skips the kitty keyboard query, wraps notifications in tmux passthrough plus a bell, warns about a slow `escape-time`, and keeps the pane title updated.

## 7. UI principles

- **Everything in a terminal, nothing fake:** box-drawing, braille spinners, colour blending; no images or unsupported escape tricks.
- **Consistent vocabulary** across modes: role glyph + colour identify an agent everywhere (`✦` planner, `◉` orchestrator, `◇`/`◆` small/big worker, `◎` QA, `▲` security); cards, peek strip and zoom all show model·effort·provider.
- **Two places, unmistakable:** the overview shows the team; a zoomed agent has a solid role-coloured header band and spine. Runs start zoomed on the planner; approving the plan lands on the overview; switching flashes the header.
- **Edges mean something:** rose animated = being prompted right now; green = running and watched; amber dotted = retrying/paused/waiting for approval; red = failed; faint dotted = not runnable yet. A halt is a full-width amber band with the reason and the key that fixes it.
- **One input everywhere**, with the same `/` commands; the stage input re-prompts the planner, `@name` targets an agent; `⏎` queues, `ctrl+f` forces.
- **Zoom is Solo:** zooming into any agent reuses the Solo view (log, diffs, plan, context), so there's one thing to learn.
- Graceful degradation: layout adapts from 40 columns to ultrawide; ASCII and 16-colour fallbacks; `reduce_motion`.

## 8. Configuration model

Three layers, each editable in the TUI and as TOML: **settings** (`codex_command`, `claude_command`, defaults, UI), **models** (aliases → provider/model, context, compaction, efforts; providers with `kind = codex | claude-code`, `auth = subscription | api_key` for Claude, keys from an env var or pasted into `api_key` and stored `0600`), **patterns** (roles with `permission`, settings with watchdog timeouts, flow). Effort resolves agent override → role → model default, clamped to what the model supports. Everything lives in `~/.mantra` (`$MANTRA_HOME` overrides): settings, models, patterns, worktrees, logs, MCP sockets and run journals (`runs/<project>-<hash>/<run>/`); nothing is written into projects, and an old `~/.config/mantra` is copied over non-destructively on first start. Patterns load from a repo-shipped `<repo>/.mantra/patterns/` (read only if present) → `~/.mantra/patterns/` → built-in, and are validated before use (unknown roles, missing flow roles, wrong kinds, bad colours/sandboxes/permissions, watchdog ordering are reported in plain language). Old pattern files without the new keys load with the defaults.

**Model discovery.** Codex's own catalog comes from `model/list`. When `claude` is on `PATH`, a `claude` provider with the six current models (+ `[1m]` variants) is added. Custom providers are queried with `GET {base_url}/models` via the system `curl`, with the key passed on stdin (never visible in `ps`). Context is read from a dozen vendor-specific fields (top level and one nested level); if absent, 200k is assumed and marked as such. Reasoning effort is enabled only when the provider advertises reasoning support or the id says `thinking`; for those models Mantra passes `model_supports_reasoning_summaries=true` so Codex actually sends the effort, and for the rest `model_reasoning_summary="none"` and no effort, which keeps strict gateways happy (verified by recording the requests real Codex sends). Discovery never overwrites values the user set, and `wire_api` is always `responses` (the only value Codex accepts), so it isn't shown or stored. The `/models` `t` test sends a `developer` message so a gateway that rejects the role fails there, not in a run.

**Approvals.** Codex fixes a turn's approval policy when the turn starts. Mantra therefore (1) sends every mode change to the live thread with `thread/settings/update` and on every `turn/start` (including the steer→new-turn race path), and (2) enforces "never ask" itself: any approval request that still arrives is answered automatically and logged. Mandala roles carry their own `permission` (default `never`), independent of the Solo mode; a role that may ask sends its requests to the inbox. The mode switch is handled before the approval card sees the key, so it works while a card is showing.

## 9. Security

Agents run inside the CLI's sandbox (Codex: planner/orchestrator read-only; workers workspace-write in their own worktree; gate agents get the integration worktree as an extra writable root). Parallel workers use approval policy `never` — they can't escalate outside their sandbox; Solo uses your approval mode. Claude Code agents run with `--dangerously-skip-permissions` by design (no interactive prompts are possible over a pipe), so their containment is the worktree, the role's `sandbox` and your review of the run branch. API keys are never written unless you paste one into a provider's `api_key` field, which is then stored `0600` and delivered to each agent's process environment only — never on argv, in logs, or in the journal (`curl` for discovery reads it from stdin). Plans and patterns are data, never executed, except gate `checks`, which are shell commands the planner proposes and **you approve as part of the plan review** (they run with a timeout in the integration worktree). The MCP bridge socket lives under `$MANTRA_HOME/run/` with the user's permissions and only speaks Mantra's tool protocol.

- `scripts/stress.sh`: every screen and overlay rendered at 13 terminal sizes through a whole simulated run (debug build, overflow checks on); the halt band; zoom vs overview; leave → `mantra runs` → `/runs` overlay → resume-last → delete; the sandbox notice; the watchdog on a lazy mock orchestrator; a worker asking a question mid-phase; plus ASCII/16-colour runs verified to emit zero non-ASCII bytes; plus real tmux 3.4 sessions driven with `send-keys`.
- `mantra mock-codex`: a protocol-faithful fake app-server with scripted planner/orchestrator/worker/gate/architect behaviours (including a deliberate 502, an out-of-scope edit, a provider that rejects a model, and a worker that vanishes for the watchdog), used by `--demo` and by headless end-to-end runs (`--snapshot "until:…;key:…;snap"` renders to a text buffer).
- `scripts/live-env.sh`: real runs against LibertAI with Codex 0.154.0 (Solo, full Mandala, compaction on a 16k window) and Claude Code 2.1.269 (headless multi-turn, steering, interrupt, `/compact`, `--resume`, MCP tools through the bridge).
