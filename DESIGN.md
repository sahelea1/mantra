# Mantra — design notes

This is the plan behind the code: what Mantra is for, how it is built, and why each decision was made. It covers the engine, protocols, resilience and configuration model; the README covers usage. Updated for v0.5.0 (the web UI and remote access: `--web` serves the running session as an installable web app, `--remote` reaches it from anywhere through an end-to-end encrypted relay, `--headless` runs either with no terminal at all — §11).

## 1. Goals and non-goals

**Goals.** One app that feels unified whether you run one agent or a team of them; every configured model available everywhere, through whichever runtime can reach it (Codex or Claude Code); model, effort and context tunable live; multi-agent workflows that are *configurable* (by hand or by an agent) rather than hard-coded; performance and robustness good enough to leave running for an hour against flaky APIs — and to survive Mantra itself being killed; works in ordinary Linux and macOS terminals; reachable from a phone or another machine — as an installable web UI, and end-to-end encrypted from anywhere through a relay that never sees plaintext — without turning Mantra into a hosted service.

**Non-goals.** Re-implementing an agent loop (Codex and Claude Code already have good ones); Windows; hiding the git workflow from the user (runs land as an ordinary branch you can inspect); a *hosted*, multi-tenant Mantra — accounts, sessions started on someone else's server — which the relay's zero-trust design leaves open for later (§12) without committing to it now.

## 2. Architecture

```
┌──────────────────────── mantra (one process, tokio, 2 worker threads) ──────────────────────────┐
│  input thread ──► AppEvent ◄── Hub events ◄── one task per agent ──► codex app-server (child)     │
│                     │                              │                  JSON-RPC over stdio         │
│                     │                              └───────────────► claude -p (child)            │
│  web server(s) ──► AppEvent::Web(Inbound) ┘                          stream-json over stdio,      │
│  (axum: HTTP, /ws, TLS, auth, push)                                  tools via `mantra mcp-bridge`│
│                     ▼                                                                              │
│   App (state, routing, approvals, commands)                                                        │
│     ├── Agent reducers: protocol notifications → renderable items, tokens, plan, file stats        │
│     ├── Run = the Conductor (deterministic state machine for Mandala; the manager beside it)        │
│     │     acts only through the `Ctx` trait: spawn / spawn_resumed / prompt / interrupt /           │
│     │     compact / stop / tool_result / set_effort / job (blocking git work off-thread) / notify   │
│     │     persists `state.json` at every transition; `engine/resume` rebuilds a Run from it         │
│     ├── UI: pure draw functions over App state (ratatui; skipped under `--headless`), redrawn       │
│     │   only when dirty/animating                                                                   │
│     └── web::Web::publish(&mut App): builds Snapshot/Delta, broadcasts to every connection (§11)     │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
        │ local / LAN, plain WS or TLS                  │ optional `--remote`: outbound only, E2EE
        ▼                                                ▼
  a browser on this machine or the LAN           relay (remote.mantra.codes, or one you run yourself):
                                                  a blind byte pipe, ≤ 1 hosted session per IPv4 ◄──►
                                                  a browser anywhere — reached by link, QR, or code+password
```

Source map: `rpc.rs` (JSON-RPC transport, stderr filter), `hub.rs` (process supervision, exit codes, crash restarts) + `hub/claude.rs` (the Claude Code process and its event translator), `bridge.rs` (`mantra mcp-bridge`: the stdio MCP server a Claude agent talks to), `agent.rs` (per-agent state + reducer), `engine/` (`pattern`, `plan`, `tools`, `git`, `run` = Conductor, `state` = persisted snapshot, `resume` = safe-boundary restart), `app.rs` (glue), `ui/` (screens), `web/` (the web UI, auth, TLS, push and the relay client — §11), `mock.rs` (simulated Codex), `discover.rs`, `config.rs`, `util.rs`.

## 3. Key decisions

**Rust, single binary.** Needed for "performant, not laggy, not bloated": no runtime, ~4 MB, starts instantly. ratatui + crossterm cover every mainstream Linux/macOS terminal.

**Drive the vendors' own agent runtimes, one process per agent.** Codex's app-server protocol (verified against Codex 0.154.0) gives threads, turns, steering, interrupts, compaction, approvals, token usage, diffs and plan updates — everything a UI needs — while keeping Codex's own loop, sandbox, auth and provider support. One process per agent costs some memory (~30–60 MB each) but buys crash isolation: a wedged or crashed agent is restarted alone (exponential backoff, max 5 restarts per 10 min, then it parks until you press `r`) and **resumes its thread**, while the rest of the team keeps working. Crash lines carry the exit code and the last useful stderr line; Codex's known chatter (`OutputTextDelta without active item`, …) is filtered and repeated lines are collapsed.

**One seam for backends.** Claude Code is driven the same way — `claude -p --input-format stream-json --output-format stream-json --verbose --dangerously-skip-permissions --session-id <uuid> --model … --autocompact …` (verified against Claude Code 2.1.269) — and `hub/claude.rs` translates its NDJSON events into the *same* notification methods `Agent::apply` already understands (`item/started`, `item/agentMessage/delta`, `item/completed`, `thread/tokenUsage/updated`, compaction items, `turn/completed`). The reducer, the Conductor and the UI have no backend branches; the only backend-aware code is the spawn (`app::spawn_agent` resolves `ProviderKind`) and the two process modules. Steering mid-turn is a stdin message (Claude delivers it at the next tool boundary), interrupt is a `control_request`, `/compact` is the literal `/compact` line (recognised by its `compact_boundary` event), crash restart is `--resume <session>`. `--dangerously-skip-permissions` is always passed: a pipe can't answer Claude's permission prompts, and Mantra's isolation comes from git worktrees and read-only roles instead (as root, Claude additionally requires `IS_SANDBOX=1`). Auth is either the user's subscription login or `--bare` + `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL` for third-party gateways — which is also the escape hatch for gateways that reject Codex's `developer` role.

**Tools reach Claude through MCP.** Codex has dynamic tools in its protocol; Claude Code does not, so each Claude agent gets `--strict-mcp-config --mcp-config` pointing at `mantra mcp-bridge --sock … --agent <id>`: a tiny stdio MCP server (same binary) that forwards `tools/list` and `tools/call` over a Unix socket in `$MANTRA_HOME/run/` to the running Mantra, which turns them into the same `item/tool/call` requests the Conductor already answers. Tools appear as `mcp__mantra__<name>`; the reply travels back over the socket. Nothing about the tool semantics changes.

**Mechanics in code, judgment in models ("the Conductor").** Spawning, waiting, retrying API errors, saving outputs, merging, running checks, archiving threads and advancing phases are done by a deterministic Rust state machine, not by an LLM looping over "check status" calls. LLM agents are only woken when judgment is needed, and they act through **dynamic tools** that Mantra executes: `mantra_submit_plan`, `mantra_revise_plan`, `mantra_spawn`, `mantra_prompt`, `mantra_retry`, `mantra_interrupt`, `mantra_set_effort`, `mantra_pause_agents`, `mantra_resume_agents`, `mantra_respawn`, `mantra_status`, `mantra_log`, `mantra_journal`, `mantra_read_phase`, `mantra_brief_orchestrator`, `mantra_resume_run`, `mantra_ask`, `mantra_ask_user`, `mantra_spawn_adhoc`, `mantra_gate_report`, `mantra_wait` (plus `mantra_read_pattern`/`mantra_write_pattern` for the architect). Tool guards refuse what can't be right (prompting a worker whose task is done once the phase moved on; a fourth prompt to the same idle worker within five minutes respawns it instead). Safety nets back up the models, e.g. tasks the orchestrator forgot to spawn are started automatically.

**Every agent that should be working is working (the watchdog).** `Run::expected_active()` derives from the stage who must be busy and why. An idle expected agent climbs a ladder — nudge it (`watchdog_seconds`), respawn the orchestrator or wake it about the idle agent (`watchdog_escalate_seconds`), at 2× wake the manager when the pattern has one (`manager_watchdog` gives it `watchdog_escalate_seconds` to react, after which `wake_planner_for_idle` runs exactly as it would without a manager), then halt — with every rung journaled. The manager is itself on the ladder while it holds a case (`Expect::Managing`): nudge, `respawn_manager` with the open escalation carried into the new brief, then the planner takes over what it held. Any run agent can be respawned in place (`Run::respawn`): the old process is stopped, a fresh one is spawned with a `[mantra:respawn]` prompt carrying the current state, and the phase/round it was in is preserved.

**Decisions travel up the chain of command.** `mantra_ask` is available to every worker, gate and finale agent (→ the orchestrator), to the orchestrator (→ the planner) and to the manager (→ the planner, which answers it by name with `mantra_prompt`); the planner and the manager have `mantra_ask_user` (→ a soft question band on the stage, answered by the user's next message — the run keeps going). `Run::pending_questions` marks the asker as waiting: its idle turn end without a `STATUS:` line is not "done", `expected_active()` skips it and expects the rung above instead (`Expect::Answering` for a planner that owes the orchestrator or the manager an answer), and the answer — `mantra_prompt` to the asker, `mantra_brief_orchestrator` for the orchestrator — clears it and bypasses the idle-prompt guards. Halts the run cannot fix itself (`GateExhausted`, `AttemptsExhausted`) go through `halt_and_escalate`: with a manager in the pattern, `escalate_to_manager` first (next paragraph); then, or without one, `escalate_to_planner`: the planner gets the failing checks, their output and the last report, and exactly three moves — `mantra_revise_plan` (`apply_revision` re-opens tasks changed after they were done, sends a phase already merging/gating back to `Orchestrating`, and `resume_by(planner)` un-halts), `mantra_resume_run(note)` (one more attempt, note to the stuck agent), `mantra_ask_user`. `spawn_task`/`retry_worker` refuse while halted. `review_tick` hands the idle orchestrator a per-worker digest every `review_minutes`.

**A manager whose job is the whole run (v0.4).** Every other agent owns a slice of the run; nothing owned the run itself, so a stall the orchestrator could not clear went straight to the planner — the most expensive agent, mid-way through a job that is not supervision. `flow.manager` names a role of kind `manager` (`""` = none; a pattern file written before v0.4 loads without one and behaves exactly as before). The seam is deliberately thin: the manager is an ordinary agent process (`spawn_manager_with`: a read-only sandbox, the role's instructions plus `MANAGER_PROTOCOL`, `manager_tools()`), with no privileged path into the engine. The engine talks to it only by prompting it — `manager_event` queues a message and `wake_manager` delivers the queue together with `overview_text` (stage and halt, plan progress, every non-worker agent with busy/idle-for and tokens, `status_text` for the workers, the journal tail) the moment it is idle — and it acts only through tools the Conductor executes under the same guards as everyone else: its `mantra_status` is that overview, `mantra_journal` the recent journal, `mantra_respawn` is `Run::respawn` for any agent (never itself). Three occasions wake it: an escalated halt (`escalate_to_manager`, the same facts the planner would get — gate or attempts exhausted, and an agent's turn failed past its free respawn, which before v0.4 went straight to the user), a watchdog case nobody below could clear (ladder rung 3), and `health_tick` every `manager_minutes` while building or in the finale — never while halted, where the escalation already has its attention. **Deadlines guarantee the chain of command never stalls on it.** An escalation carries `ManagerEscalation { deadline = max(watchdog_escalate_seconds, 120 s), reminded }`: a turn it ends without resuming, restarting or asking gets one reminder, and the next such turn — or the deadline, once it is idle and not waiting on the planner or the user — hands the halt on (`manager_gave_up`): to `escalate_to_planner` for gate/attempts exhausted, and for a failed turn to nobody but the user — the planner may be the very agent that is failing, and no plan change fixes a broken process; a watchdog case has the same deadline in `manager_watchdog`, closed by a completed manager turn, and a silent manager is respawned for it once, then the planner is woken; `manager_tick` runs while halted, unlike every other wake. `lift_halt_for_restart` encodes "restarting an agent is the decision to go on": `mantra_retry`/`mantra_respawn` during an escalated halt resume the run first (an `AttemptsExhausted` task gets `extra_attempts += 1`) so the restart is accepted instead of refused by the halted guard. Two choices follow from its job. It is spawned when the first phase starts (`start_phase(0)` → `ensure_manager`), not at planning: there is nothing to supervise before there is a team, and a planning stall already has its own rungs; on `mantra runs resume` it is re-attached to its thread (`resume_manager`), because its memory of the run is the point of it. And a manager whose turn fails past the retries is dropped (`manager = None`, whatever it held goes on to the next rung — the planner, or the user for a failed-turn halt — and a fresh one comes with the next escalation or health digest) rather than halting: a supervisor that stops the build it supervises would be worse than none.

**A hand stop outranks every self-healing path.** `Agent::stopped_by_user` is set only by the two user interrupts (`ctrl+c`, `x` — never by `Run::halt`, `mantra_interrupt` or `mantra_pause_agents`, which have their own resume paths) and cleared at exactly one choke point, `app::prompt_agent`: talking to an agent *is* telling it to carry on. While set, `Run::on_turn_done` returns before the retry ladder, the planner nudge, the gate round, the worker report and the finale step; `on_ready` skips the post-restart resume prompt; `watchdog_tick` steps over it; `status_text` marks it. This is what keeps the engine from undoing a deliberate stop — the failure it fixes had three separate paths (nudge, transient retry, resume) putting a stopped planner back to work within seconds.

**Liveness is shown, not inferred.** The CLIs tick while a model reasons (Claude Code emits `thinking_tokens` every 1-2s), so `Agent::last_event` standing still is the one honest "is it stuck?" signal: `ui::quiet_for` surfaces it past 20s on the status line and the agent card, and `watchdog_tick` journals one line per silent spell for a busy non-worker agent past `stall_minutes` (workers keep `tick`'s tripwire, which also wakes the orchestrator). The tick's own running count goes into the activity label (`thinking · 9.4k`) so the number visibly climbs. Claude Code's `autocompact_state` announces the account's real context window seconds after spawn; a subscription login trusts it over the configured guess, an `api_key` gateway does not.

**Halts are typed.** There is no `paused` flag. Everything that stops a run goes through `Run::halt(reason, agent, message)` with `HaltReason::{User, Auth, UsageLimit, ProviderRejected, Environment, GateExhausted, AttemptsExhausted, AgentTurnFailed}`; the reason drives the band's hint (`m` to switch a rejected model, `r` to retry an environment fix, `space` to resume a user pause) and `resume()` is the single way back. `ProviderRejected` (HTTP 400/422, "unexpected message role") is never retried. Two consecutive identical gate blockers halt (`GateExhausted`) rather than burn the remaining rounds; the first `bwrap`/user-namespace failure halts (`Environment`) with the sysctl fix — and the same probe runs once at startup, before a run can start.

**The plan is a validated contract.** The planner submits JSON matching a schema: phases → tasks (`id`, `title`, `role`, `scope` globs, self-contained `prompt`, `acceptance`, optional `effort`) + a per-phase gate (`checks`, `focus`, `criteria`) + `final_checks` + `orchestrator_brief`. Mantra validates it (unique ids, known worker roles, non-trivial prompts, per-phase task caps, and **pairwise-disjoint scopes for parallel tasks**) and returns human-readable rejections so the planner fixes them itself. Revisions are diffed against the running phase so completed work is kept.

**Isolation by git worktrees.** Each run gets an integration worktree on branch `mantra/<run>`; each parallel worker gets its own worktree on `mantra-w/<run>/<task>-<attempt>` (a separate namespace, since git can't nest refs under an existing branch). At the gate Mantra commits and merges each worker branch (`--no-ff`); conflicts go to the QA gate agent, whose sandbox is widened to the integration worktree via `writable_roots`. Out-of-scope edits trip a wire that wakes the orchestrator. `isolation = auto` falls back to a shared directory for non-git projects; if a single worktree can't be created, that worker runs on the integration copy (safe because scopes are disjoint). `/land` merges the run branch into your branch only when your tree is clean; `mantra runs delete` removes worktrees, branches and the journal.

**Runs are resumable.** `state.json` is a typed `RunState` (stage, workspace, workers with worktree/branch/report, agents with thread ids, completed phases) rewritten atomically at every transition and whenever an agent's thread id becomes known. `engine/resume` rebuilds a `Run` from it and restarts at the nearest **safe boundary** rather than replaying what the old process was mid-way through: Planning → planner re-attached to its thread (`Ctx::spawn_resumed`) and asked to submit; Review → the saved plan back up for review; a working phase → a fresh orchestrator briefed with the phase status, running workers re-attached when their worktree still exists (`thread/resume` / `--resume`) or re-spawned with the same prompt; merging/checks/gate → the idempotent merge → checks → gate sequence again; handoff → next phase; finale → the step again; done/failed → read-only. Old v0.1 `state.json` files (untyped stage) are listed but refused.

**Context management.** Every agent is launched with an explicit window and compaction threshold — the model's numbers or an assumed 200k / 85% (marked as assumed in the UI): `model_context_window`/`model_auto_compact_token_limit` for Codex, `--autocompact` for Claude — so a 16k model compacts instead of dying, and a worker that still overflows on an assumed window gets it halved for the next attempt. Compaction is shown honestly: Codex reports it as a `contextCompaction` item (plus a deprecated `thread/compacted` twin, which Mantra ignores when the item is present); Claude as `compact_boundary` with pre/post token counts. Mantra records the size before, amends the item with the size after, and treats a turn that contains *only* a compaction as housekeeping, not as "the agent finished" — otherwise the Conductor would mistake a compaction for a completed planner/orchestrator/worker turn. A `/compact` sent mid-turn is deferred to the end of the turn. Workers are short-lived and archived after their phase (report and exit status saved first). The orchestrator is reset per phase with a compact handoff (or compacted in place: `orchestrator_context = fresh|compact`).

**Messages queue behind a turn.** In every chat (Solo, zoom, `@name`), `⏎` while the agent is mid-turn queues the message (visible chip) and delivers it when the turn ends; `ctrl+f` force-steers it into the running turn now. The engine's own prompting (`Send::Auto`) keeps steering immediately, as before; only user-originated sends carry `Send::Queue|Force`.

## 4. The default workflow as a state machine

```
Setup ─► Planning ─► Review ─► Phase[i]: Orchestrating ─► Merging ─► Checks ─► Gate(round ≤ N) ─► Handoff ─┐
            ▲  (user feedback)                                                                             │
            └──────────── re-prompt: planner may pause agents / revise plan / brief orchestrator ◄─────────┤
                                                                                   next phase ◄────────────┘
                                                               last phase ─► Finale[step…] ─► Done | Failed
   any stage ─► Halt{reason} ─► resume()          any stage ─► state.json ─► (new process) resume at a boundary
```

The manager (`flow.manager`) sits beside this machine rather than in it: spawned at `Phase[0]`, alive until `Done | Failed`, woken by escalated halts, watchdog rung 3 and `health_tick`. The finale is a list in the pattern (default: heavy QA → security → planner verification with `may_spawn = true`). The whole flow is data: roles, which role plans/manages/orchestrates/gates/handles re-prompts, and the finale chain are all editable in the Studio.

## 5. Resilience and cost control

| failure | handling |
|---|---|
| stream drop / overload / 429 / 5xx | the CLI retries the stream; Mantra then retries the turn with backoff (4s, 8s, …), up to `worker_retries + 1` |
| context window exceeded | compact, then continue; halve an *assumed* window for the next attempt |
| 401 / 403 / usage limit | **halt** (`Auth`/`UsageLimit`), alert + desktop notification, `space` resumes |
| HTTP 400/422, "unexpected message role" | **halt** (`ProviderRejected`), never retried; `m` switches the role's model and resumes |
| `bwrap` / user-namespace failure | **halt** (`Environment`) on the first one, with the sysctl fix; probed at startup too |
| planner / orchestrator / gate turn fails otherwise | one free respawn, then **halt** (`AgentTurnFailed`) — never nag in a loop; the manager gets it first (`mantra_respawn` lifts it), then the user (`r`) — never the planner, which may be the failing agent |
| the manager's own turn fails | dropped, never a halt: what it held goes to the next rung (the planner, or the user for a failed-turn halt), a fresh manager comes with the next escalation or health digest |
| gate keeps failing, repeats the same blocker, or the same check fails identically twice | **halt** (`GateExhausted`) and **escalate**: the manager first (hint / retry / respawn / ask the planner), the planner after its deadline (revise / resume with a note / ask the user) |
| worker fails for good | reported to the orchestrator, who may steer or respawn; **hard cap** of `worker_retries + 3` attempts per task across every path, then **halt** (`AttemptsExhausted`) and escalate the same way; `r`, the manager's `mantra_retry`/`mantra_resume_run` or the planner grants one more |
| a worker or gate is unsure | `mantra_ask` up one rung; it waits, the rung above is expected to answer |
| an expected agent goes idle | watchdog ladder: nudge → respawn/wake orchestrator → wake manager → wake planner → halt; a manager idle on a case: nudge → respawn → the planner takes over |
| codex / claude process crash | restart that agent only, resume thread/session; parks after 5 crashes / 10 min |
| worktree creation fails | fall back to the shared integration copy |
| stall / token budget / out-of-scope edit | tripwire event to the orchestrator |
| Mantra itself dies | `mantra runs resume <id>` from the last `state.json` |

Unrecognised errors are classified from the message (401/403/forbidden → auth; 400/422/invalid request → provider-rejected; 429/502/503/disconnect → transient). Every turn Mantra starts is tracked (`awaiting_start`), so prompts sent during a turn start are queued and delivered as steering; failed steers are re-queued for the next turn. Starting a run pre-flights every role's provider (missing key, unknown alias) so no turn is spent on a `Missing environment variable` error.

## 6. Performance

Rendering is event-driven: the loop redraws only when state changed or something is animating (capped at `fps`, default 12); an idle Solo session renders at 0 fps. Bursts of streaming deltas are drained (up to 512 events) before a single redraw. Rendered lines are cached per item (invalidated by version, width, verbosity), and the log renders bottom-up so only visible items are laid out. Item history is capped per agent (3000, oldest trimmed). Animations are pure functions of time. Blocking git work runs on `spawn_blocking`. `state.json` is a few KB written atomically (temp + rename) on transitions only.

**Terminal robustness.** Drawing happens inside `catch_unwind` (the panic hook skips terminal restoration while drawing), so a layout bug shows a one-line notice instead of killing every agent. Layout arithmetic is saturating throughout and verified by rendering all screens at 13 sizes in a debug build. Frames are wrapped in synchronized-output sequences. Under tmux, Mantra avoids the prefix key (`ctrl+t` toggles panels), skips the kitty keyboard query, wraps notifications in tmux passthrough plus a bell, warns about a slow `escape-time`, and keeps the pane title updated.

## 7. UI principles

- **Everything in a terminal, nothing fake:** box-drawing, braille spinners, colour blending; no images or unsupported escape tricks.
- **Consistent vocabulary** across modes: role glyph + colour identify an agent everywhere (`✦` planner, `◈` manager, `◉` orchestrator, `◇`/`◆` small/big worker, `◎` QA, `▲` security); cards, peek strip and zoom all show model·effort·provider.
- **Two places, unmistakable:** the overview shows the team (the planner and, from 90 columns, the manager as mini-cards flanking the orchestrator; in the finale the manager sits above the ad-hoc fixes); a zoomed agent has a solid role-coloured header band and spine. Runs start zoomed on the planner; approving the plan lands on the overview; switching flashes the header.
- **Edges mean something:** rose animated = being prompted right now; green = running and watched; amber dotted = retrying/paused/waiting for approval; red = failed; faint dotted = not runnable yet. A halt is a full-width amber band with the reason and the key that fixes it.
- **One input everywhere**, with the same `/` commands; the stage input re-prompts the planner, `@name` targets an agent; `⏎` queues, `ctrl+f` forces.
- **Zoom is Solo:** zooming into any agent reuses the Solo view (log, diffs, plan, context), so there's one thing to learn.
- Graceful degradation: layout adapts from 40 columns to ultrawide; ASCII and 16-colour fallbacks; `reduce_motion`.

## 8. Configuration model

Three layers, each editable in the TUI and as TOML: **settings** (`codex_command`, `claude_command`, defaults, UI), **models** (aliases → provider/model, context, compaction, efforts; providers with `kind = codex | claude-code`, `auth = subscription | api_key` for Claude, keys from an env var or pasted into `api_key` and stored `0600`), **patterns** (roles of kind `planner | manager | orchestrator | worker | gate` with `permission`, settings with watchdog timeouts, `review_minutes` and `manager_minutes`, flow with an optional `manager`). Effort resolves agent override → role → model default, clamped to what the model supports. Everything lives in `~/.mantra` (`$MANTRA_HOME` overrides): settings, models, patterns, worktrees, logs, MCP sockets and run journals (`runs/<project>-<hash>/<run>/`); nothing is written into projects, and an old `~/.config/mantra` is copied over non-destructively on first start. Patterns load from a repo-shipped `<repo>/.mantra/patterns/` (read only if present) → `~/.mantra/patterns/` → built-in, and are validated before use (unknown roles, missing flow roles, wrong kinds, bad colours/sandboxes/permissions, watchdog ordering are reported in plain language). Old pattern files without the new keys load with the defaults — and, with no `flow.manager`, without a manager.

**Model discovery.** Codex's own catalog comes from `model/list`. When `claude` is on `PATH`, a `claude` provider with the six current models (+ `[1m]` variants) is added. Custom providers are queried with `GET {base_url}/models` via the system `curl`, with the key passed on stdin (never visible in `ps`). Context is read from a dozen vendor-specific fields (top level and one nested level); if absent, 200k is assumed and marked as such. Reasoning effort is enabled only when the provider advertises reasoning support or the id says `thinking`; for those models nothing extra is configured — Codex ≥ 0.150 sends `reasoning.effort` to any model once the turn carries one, and the `model_supports_reasoning_summaries` key it used to need is unrecognised now (passing it put a *Codex is ignoring 1 unrecognized configuration setting* banner at the top of every agent log) — and for the rest `model_reasoning_summary="none"` and no effort, which keeps strict gateways happy (verified by recording the requests real Codex sends). Discovery never overwrites values the user set, and `wire_api` is always `responses` (the only value Codex accepts), so it isn't shown or stored. The `/models` `t` test sends a `developer` message so a gateway that rejects the role fails there, not in a run.

**Approvals.** Codex fixes a turn's approval policy when the turn starts. Mantra therefore (1) sends every mode change to the live thread with `thread/settings/update` and on every `turn/start` (including the steer→new-turn race path), and (2) enforces "never ask" itself: any approval request that still arrives is answered automatically and logged. Mandala roles carry their own `permission` (default `never`), independent of the Solo mode; a role that may ask sends its requests to the inbox. The mode switch is handled before the approval card sees the key, so it works while a card is showing.

## 9. Security

Agents run inside the CLI's sandbox (Codex: planner/manager/orchestrator read-only; workers workspace-write in their own worktree; gate agents get the integration worktree as an extra writable root). Parallel workers use approval policy `never` — they can't escalate outside their sandbox; Solo uses your approval mode. Claude Code agents run with `--dangerously-skip-permissions` by design (no interactive prompts are possible over a pipe), so their containment is the worktree, the role's `sandbox` and your review of the run branch. API keys are never written unless you paste one into a provider's `api_key` field, which is then stored `0600` and delivered to each agent's process environment only — never on argv, in logs, or in the journal (`curl` for discovery reads it from stdin). Plans and patterns are data, never executed, except gate `checks`, which are shell commands the planner proposes and **you approve as part of the plan review** (they run with a timeout in the integration worktree). The MCP bridge socket lives under `$MANTRA_HOME/run/` with the user's permissions and only speaks Mantra's tool protocol.

## 11. Web UI and remote access

`--web` starts an HTTP+WebSocket server *in the same process* as the TUI (`src/web/`); `--remote` additionally dials out to a relay so the same UI reaches you from anywhere; `--headless` runs either with no terminal at all. All three are optional — the code is always compiled in, but nothing is bound and no cost is paid unless one of them is given.

**Process architecture: one owner, one event loop.** `App` stays the single owner of all state; the web server only ever holds channels, never `&App` across an `.await`. A new `AppEvent::Web(Inbound)` — a connection id, a request id and a parsed `Command` — joins the same event loop `AppEvent::Term` and the hub's events already use, handled by `App::web_command` (`web/commands.rs`) exactly like a keypress is handled today; replies and broadcasts go out through channels the event loop owns (`Web::reply`/`Web::publish`), so no lock is ever held across an await. `event_loop` takes `Option<&mut Terminal<B>>`: with a terminal it draws as before; with `None` (`--headless`) it skips drawing, raw mode and the input thread but keeps ticking, publishing and notes — one function, not two paths to keep in sync. A published snapshot lags reality by at most the publish cadence (~66 ms), the same order of magnitude a human typing would call instant.

**Protocol: a snapshot, then deltas, `seq`-numbered.** Every connection gets a full `Snapshot` on `hello` (app info, every agent's metadata, the current run, plan, approvals, toast, a recent slice of each agent's transcript and pulse); after that, only `Delta`s — section-by-section diffs against the last published snapshot, with an item's text sent as an append when the previous text is a strict prefix of the new one, and nothing sent at all when nothing changed. A client that misses a `seq` (a reconnect) says so in its next `hello` and gets a fresh full snapshot; deltas are never replayed or queued per client — broadcasting the same bytes to everyone is what keeps `publish` cheap as the number of connections grows. Commands (`send`, `approve`, `respawn`, `set_model`, `plan_approve`, `land`, …) are the same vocabulary of actions Solo/Stage/Zoom already expose from the keyboard, executed on the App task and answered with a `result` keyed by the request id the client chose — nothing the web UI can do reaches further into the engine than a keypress already could.

**Auth: a password, a cookie, and nothing else in v1.** A loopback-only listener needs no password (anyone who can reach it can already run `mantra` itself); any other bind refuses to start without one. `PasswordAuth` compares the configured password in constant time, mints a random session token on success, and stores only its SHA-256 in `$MANTRA_HOME/web/sessions.json` (capped, oldest evicted, expiring when idle); the cookie is `HttpOnly; SameSite=Strict` (+`Secure` under TLS) and every request also checks `Origin` against `Host`, so a malicious site open in the same browser cannot call the API. Login is rate-limited per source IP with an exponential lock-out, and again globally against a distributed storm. `Authenticator` is a trait for exactly this reason: a future hosted version (§12) swaps in an account-backed implementation without touching the protocol or the rest of the UI.

**TLS: a certificate authority Mantra owns, not a leaf you re-trust every time.** `--web-tls` does not hand out a bare self-signed certificate (which a browser would need re-trusting whenever the machine's address changes); it makes a small private CA once, under `$MANTRA_HOME/web/tls/`, and signs a leaf for every name the machine currently answers to (`localhost`, loopback, the LAN IPv4 the OS would pick for an outbound connection, the hostname, plus `[web] sans`), reissuing the leaf — never the CA — only when that set changes or it is close to expiring. `/cert.pem` hands out the CA alone; installing *that* once on a device is enough to trust every certificate this Mantra ever issues for itself afterwards. `--web-cert`/`--web-key` skips all of this for a certificate you already have.

**Push: hand-rolled, not a dependency.** Mantra already carries a TLS stack, `p256`, HKDF and AES-GCM for the relay, so Web Push (RFC 8291 payload encryption plus a VAPID JWT, `web/push.rs`) is built on those instead of pulling in a push-specific HTTP client. Six kinds of note (halt, question, approval, plan review, run done, Solo turn finished) map to a notification carrying its own `Topic` (so a second halt replaces the first rather than stacking two), each togglable per device; delivery runs on its own task so the event loop never awaits the network, a permanently failing subscription (404/410, or several failures in a row) is dropped, and the endpoint is never logged in full.

**The relay: end-to-end encrypted, and blind on purpose.** `remote.mantra.codes` (or any relay speaking the same wire format) is deliberately kept dumb: it demultiplexes binary frames between one host and many browser clients by a routing id (`sid`) and a bearer token only the host holds, and never sees a decrypted byte. The host and a connecting browser derive a shared key from the link's fragment or the code+password (PBKDF2 for the base key, a fresh per-connection HKDF key from a hello exchange of nonces), then speak the *same* JSON protocol as a local WebSocket, wrapped in AES-256-GCM frames with a strictly increasing per-direction counter — an out-of-order or replayed frame is a protocol violation, not silently accepted, and a failed decrypt counts a strike against the client's relay-reported IP. Because the relay only forwards ciphertext, **the site that serves the web app and the relay that forwards its bytes need not be the same host, or run by the same person**: `--remote-site` (`[web] remote_site`) points a link at wherever the app is actually served, defaulting to the relay's own origin. This also means Mantra depends on `remote.mantra.codes` for nothing but a default: any relay speaking §10.2–10.3 of the design spec works, self-hosted or not, and the reference relay implementation is deliberately kept out of this repository (a separate, Docker-shaped deliverable) so it can be operated, upgraded and relocated independently of this binary's release cadence.

**One hosted session per IPv4 address.** The relay accepts at most one *hosting* connection (a running `mantra --remote` process) per source IPv4 address at a time; a second host dialling in from behind the same address is refused with HTTP 409 until the first disconnects. This is a relay-side policy (`--max-hosts-per-ip`), not something the client enforces — the client only parses and reports the refusal as a sentence a person can act on, rather than a raw status code — but it shapes the client's own dialling code too: a host must resolve and connect to the relay over IPv4 specifically (an IPv6-only relay address is rejected before it ever tries to connect, and the relay itself answers an IPv6 peer with 403), because the one-session rule is keyed on the IPv4 address the relay observes the TCP connection arrive from.

## 12. Next steps

Hosted sessions on mantra.codes (design notes only, unbuilt): the relay's zero-trust design already gives location independence with no trust required in the server, so a hosted version would add an `Authenticator` backed by mantra.codes accounts, a session router that starts `mantra --headless --remote` containers on demand and hands the user the link, a `MANTRA_HOME` per container, and project checkout via git credentials the user supplies — the relay and the wire protocol would not change, and "one hosted session per IPv4" becomes a non-issue once every container has its own address in the pod network. Also: per-run cost estimates from token usage; MCP elicitation UI; saved layouts; optional parallel phases (DAG instead of a chain) once the linear flow has proven itself; a Claude Code `permission` mode that answers `can_use_tool` control requests over the pipe so Claude roles could ask like Codex roles do.
